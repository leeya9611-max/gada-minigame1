기준: `docs/야리끼리_한달챌린지_피벗기획_v1.md` · 기존 코드(작업지시서 v2의 WP0~6.5 완료 상태) · 2026-07

## E1. 엔들리스 "무한 잔업 모드" (랭킹 본선)

목표: WP6에서 노선(레벨) 재생으로 바뀐 엔진에 **레벨 없이 무한히 달리는 모드**를 되살린다. 이벤트 랭킹의 유일한 점수 소스.
대상: `GameEngine.ts`(mode 상태·절차 스폰 경로), `config.ts`(엔들리스 밸런스), `types.ts`/`lib/api.ts`(결과값 mode 필드).
완료 기준(AC):
- `engine.setEndless()`(또는 동급 API)로 시작하면 레벨 데이터 없이 절차 스폰(장애물·코인·아이템·투척)으로 무한 진행.
- 완주 판정·피날레 돌진 없음. 속도는 BASE에서 지속 램프(MAX 상한), 박소장 추격(gap)·HP 실패 조건은 동일.
- 점수 산식 유지(코인×10+거리÷10). 결과값에 `mode: "endless" | "edu" | "route"` 추가, 엔들리스는 `routeId: "endless"`.
- 기존 노선 재생 경로는 그대로 동작(안전교육이 사용).

```
[클로드코드 프롬프트 — E1]
docs/야리끼리_한달챌린지_피벗기획_v1.md 2장대로 엔들리스 모드를 복원해줘.
1) GameEngine에 mode("route" | "endless") 상태를 추가하고, setEndless() 시작 API를 만들어.
   엔들리스는 레벨 데이터 없이 예전 절차 스폰(SPAWN 상수 기반 장애물/코인/아이템/투척 랜덤 스폰)으로 무한 진행.
   완주 판정과 ROUTE.FINALE 돌진은 엔들리스에서 비활성. 속도는 SPEED.BASE에서 ACCEL로 램프(MAX 상한).
   박소장 추격(gap)·HP 실패 조건, 점수 산식은 그대로.
2) 결과값(GameResult)에 mode 필드를 추가하고 엔들리스는 routeId "endless"로 전달. lib/api.ts 타입도 갱신.
3) 기존 노선 재생(setLevel) 경로는 건드리지 말 것(안전교육에서 계속 사용).
4) 임시 확인용으로 로비에서 엔들리스를 시작할 수 있는 개발용 진입을 하나 만들어(다음 단계 E2에서 정식 버튼으로 교체).
npx tsc --noEmit 통과 확인하고 실제 플레이(무한 진행·게임오버·결과 전달)로 검증한 뒤 변경 요약 보여줘.
```

## E2. 로비 2버튼 개편 + 안전교육 게이트

목표: 월드맵(노선 5개 선택)을 걷어내고 로비를 [안전교육] [무한 잔업 모드] 2버튼으로. 안전교육 1회 이수가 본선 해금 조건.
대상: `Game.tsx`(LobbyScreen 교체), `lib/progress.ts`(이수 플래그), 티켓 정책 분기.
완료 기준(AC):
- 로비: 닉네임·티켓 잔량 + 큰 버튼 2개. 무한 잔업 모드는 안전교육 미이수 시 잠금 표시("안전교육 이수 후 참가 가능").
- 안전교육: **티켓 미차감**, 언제든 재입장 가능. 완주 시 이수 플래그 저장(우선 localStorage, 서버 이관 TODO 주석) → 본선 즉시 해금 + "무한 잔업 모드 개방!" 안내.
- 무한 잔업 모드: 티켓 1장 차감(기존 consumeTicket), 0이면 충전 화면(S5) 기존 흐름.
- 별점·해금·월드맵 UI 제거(관련 함수·데이터는 삭제하지 말고 미사용 보관). 상점 버튼 제거(WP7 취소).
- 완주 성공 화면(S3a)은 안전교육 전용이 되고, 버튼은 [무한 잔업 모드 가기]/[다시 연습]으로.

```
[클로드코드 프롬프트 — E2]
docs/야리끼리_한달챌린지_피벗기획_v1.md 2장·2.5대로 로비를 개편해줘.
1) LobbyScreen을 월드맵에서 2버튼 구성으로 교체: [안전교육](부제 "조작 연습 · 무료")과
   [무한 잔업 모드](부제 "랭킹전 · 티켓 1장"). 헤더의 닉네임·티켓 표시는 유지, 상점 버튼은 제거.
2) lib/progress.ts에 안전교육 이수 플래그(loadEduDone/saveEduDone, localStorage, 서버 이관 TODO 주석)를 추가해.
3) 안전교육 시작은 티켓을 차감하지 않게 startRoute와 분리하고, route1 레벨로 재생(E3에서 route_edu로 교체 예정).

4) 무한 잔업 모드 버튼은 이수 전 잠금(회색 + "안전교육 이수 후 참가 가능"), 이수 후 티켓 차감하고 engine.setEndless()로 시작.
5) 별점·월드맵 관련 UI 코드는 렌더에서만 떼고 함수·route2~5 데이터는 보관. E1의 개발용 진입은 제거.
npx tsc --noEmit 통과, 신규 유저 흐름(교육→해금→본선)과 재방문 흐름(로비 직행)을 확인하고 요약 보여줘.
```

## E3. 안전교육 노선 — 한 판 안 구간 학습

목표: 안전교육 전용 레벨 `route_edu`를 만들고, 구간별 기술 학습(점프→이단점프→슬라이드→투척→미니 추격→정류장)과 안내·관용 룰을 넣는다.
대상: `public/levels/route_edu.json`(신규), `level.ts`(안내 마커 확장), `GameEngine.ts`(교육 모드 룰), `Game.tsx`(구간 배너).
완료 기준(AC):
- route_edu: 90초 내외, 구간 1 웅덩이(점프)만 → 2 자재더미·연속(이단점프) → 3 lowbar(슬라이드) → 4 투척 '!'(상·하) → 5 짧은 추격 압박 후 정류장. 초반 속도 낮게(baseSpeed 260 내외), 램프 완만.
- 레벨 데이터에 구간 안내 마커(예: `markers: [{col, text}]`)를 추가하고 해당 col 통과 시 상단 배너로 2초 표시("탭해서 점프!" 등, 기획 2.1 표 문구).
- 신규 요소 첫 등장 col 직전에 일시 감속(예: 0.7배 2초) 1회씩.
- 교육 모드 관용: 피격 시 HP 미감소(넉백·감속 연출은 유지) + gap 실패 없음(잡히기 직전까지만 압박). 즉 실패 없이 완주 유도.
- 투척은 구간 4부터만 발생(그 전 GRACE).

```
[클로드코드 프롬프트 — E3]
docs/야리끼리_한달챌린지_피벗기획_v1.md 2.1대로 안전교육 노선을 구현해줘.
1) public/levels/route_edu.json 생성(map-editor 포맷). 90초 내외, baseSpeed 260, 구간 구성:
   1 웅덩이 점프만 → 2 자재더미·연속 장애물(이단점프) → 3 lowbar 슬라이드 → 4 투척 상·하 회피 → 5 미니 추격 → 정류장.
   코인은 각 구간 동선을 따라 배치해 조작을 유도해.
2) LevelData에 markers?: {col:number; text:string}[] 를 추가하고, 통과 시 상단 배너로 2초 표시:
   "탭해서 점프!"/"공중에서 한 번 더!"/"아래로 밀어(왼쪽 꾹) 슬라이드!"/"!가 뜨면 피하세요"/"정류장이 보인다! 달려!"
3) 신규 요소 첫 등장 직전 1회 일시 감속(0.7배 2초).
4) 교육 모드(edu) 룰: 피격 시 HP 미감소(피격 연출·감속은 유지), gap<=0 실패 비활성(최소 gap에서 클램프),
   투척은 구간 4부터. E2의 안전교육 시작을 route_edu로 교체.
npx tsc --noEmit 통과, 처음 하는 사람 기준으로 실패 없이 완주되는지 플레이 확인 후 요약 보여줘.
```

## E7. 운영 DB 연결 — Vercel 배포 + Supabase(Postgres) (2026-07-30)

목표: `app/api/nickname`·`app/api/season`의 `globalThis` 메모리 스텁을 Supabase Postgres로 교체.
계약(요청/응답 형태)은 **각 route.ts 상단 주석 그대로 유지** — 클라이언트 코드는 손대지 않는다.
안전교육 이수 플래그(현재 localStorage)도 같이 서버 이관.

**범위 밖(옮기지 말 것)**: 티켓·포인트 등 재화. 지급·차감 권위는 네이티브/가다 서버 유지.

### E7-0. 사용자가 직접 하는 준비 (코드 작업 전)

1) Supabase에서 새 프로젝트 생성(리전 Seoul 권장).
2) SQL Editor에 아래를 그대로 실행:

```sql
-- 유저(닉네임 + 안전교육 이수)
create table if not exists users (
  user_id      text primary key,
  nickname     text,
  nickname_key text unique,           -- 공백제거·소문자 (중복 판정용)
  edu_done     boolean not null default false,
  created_at   timestamptz not null default now()
);

-- 일일 베스트 (하루 1행, 그날 최고점만 유지)
create table if not exists daily_scores (
  user_id    text not null references users(user_id) on delete cascade,
  play_date  date not null,           -- KST 기준 날짜
  best_score integer not null default 0,
  updated_at timestamptz not null default now(),
  primary key (user_id, play_date)
);
create index if not exists idx_daily_scores_date on daily_scores (play_date);

-- RLS 켜고 정책은 두지 않음 → anon 키로는 접근 불가, 서버(service_role)만 통과
alter table users enable row level security;
alter table daily_scores enable row level security;

-- 프로젝트 생성 시 "Automatically expose new tables"를 껐다면 권한을 직접 부여해야 한다.
-- service_role(서버 전용)에만 주고 anon/authenticated에는 아무것도 주지 않는다.
grant usage on schema public to service_role;
grant all on table users, daily_scores to service_role;

-- 랭킹 TOP N
create or replace function season_board(p_from date, p_to date, p_top int)
returns table (rank bigint, nickname text, week_score bigint)
language sql stable as $$
  select row_number() over (order by sum(d.best_score) desc, min(d.user_id)) as rank,
         coalesce(u.nickname, '이름없는 노동자') as nickname,
         sum(d.best_score) as week_score
  from daily_scores d
  join users u on u.user_id = d.user_id
  where d.play_date between p_from and p_to
  group by d.user_id, u.nickname
  having sum(d.best_score) > 0
  order by week_score desc
  limit p_top;
$$;

-- 내 순위
create or replace function season_me(p_from date, p_to date, p_user text, p_today date)
returns table (rank bigint, week_score bigint, today_best int)
language sql stable as $$
  with agg as (
    select d.user_id,
           sum(d.best_score) as week_score,
           row_number() over (order by sum(d.best_score) desc, min(d.user_id)) as rank
    from daily_scores d
    where d.play_date between p_from and p_to
    group by d.user_id
    having sum(d.best_score) > 0
  )
  select a.rank, a.week_score,
         coalesce((select best_score from daily_scores
                   where user_id = p_user and play_date = p_today), 0)
  from agg a where a.user_id = p_user;
$$;

-- RPC 실행 권한도 service_role에만
grant execute on function season_board(date, date, int) to service_role;
grant execute on function season_me(date, date, text, date) to service_role;
```

3) Project Settings → API에서 **Project URL**과 **service_role key** 복사.
4) 로컬 `.env.local`(gitignore 확인)과 Vercel 프로젝트 환경변수 양쪽에 등록:

## E8. 모바일 성능 최적화 — 렉 해소 (2026-07-31 배포 테스트)

증상: 배포본을 모바일에서 플레이하면 렉이 심함. 인앱 브라우저·사파리 양쪽 동일 → 웹뷰 문제가
아니라 코드 문제로 확정.

### 원인 분석 (코드 실측)

**① 배경 레이어를 매 프레임 대형 원본에서 축소 렌더 (최대 원인)**

`public/assets/maps/map1/` 실측 크기:

| 레이어 | 원본 | 표시 크기 | 매 프레임 리샘플 |
|---|---|---|---|
| sky | 2822×700 | 약 1370×340 | 약 200만 px |
| silhouette | 2524×560 | 약 1262×280 | 약 140만 px |
| ground | **7584×200** | 약 4171×110 | 약 750만 px |

`Background.tile()`이 `ctx.drawImage(img, x, dy, dw, dh)`로 **원본 크기 소스를 매 프레임 축소**한다.
합계 약 1100만 소스 픽셀을 프레임마다 리샘플하는 셈. 게다가 mirror 분기는 `translate`+`scale(-1,1)`
변환 경로라 GPU 캐시가 잘 안 먹는다. 데스크톱에선 묻히지만 모바일 GPU에선 이게 지배적 비용.

**② 로드 시 대형 캔버스 픽셀 루프**

`filterCache()`/`themeCache()`가 위 원본 크기 그대로 `getImageData` → JS 픽셀 루프 →
`putImageData`. 약 500만 px(silhouette는 filter+theme 2회). 초기 멈춤 + 원본과 별도로 남는
대형 캔버스가 iOS 캔버스 메모리를 압박.

**③ 효과음이 HTMLAudioElement**

`lib/sfx.ts`가 `new Audio()` 12개 + BGM 스트리밍. iOS에서 `play()` 호출마다 메인 스레드 히치가
생기고, 코인은 초당 여러 번 울린다.

### E8-1. 배경 프리스케일 (최우선)

```
[클로드코드 프롬프트 — E8-1]
app/game/engine/Background.ts 렌더 비용을 줄여라. 목표: 매 프레임 축소 리샘플 제거,
per-frame drawImage를 1:1 블릿으로.

1) 레이어별 "표시 크기 캔버스"를 로드 시 1회 굽는다.
   - 현재 draw()가 각 레이어를 (dw, dh)로 그리는데, 그 dh는 GROUND_Y/SIL_H/VIEW.GROUND_H로
     고정이라 로드 시점에 계산 가능하다. dw = iw * (dh/ih).
   - 파이프라인 순서: 원본 로드 → **표시 크기로 축소한 캔버스 생성** → 그 위에서 filterCache/
     themeCache 픽셀 처리 → mirror 베이크. (축소를 먼저 해야 픽셀 루프 비용도 같이 떨어진다)
   - DPR 대응: 표시 크기 × min(2, devicePixelRatio)로 구워서 선명도 유지. ctx가 이미 dpr 스케일
     되어 있으므로 drawImage 목적지 크기는 CSS px 기준 그대로 둘 것.
2) mirror 타일링도 1회 베이크로 바꾼다.
   - 폭 2×dw 캔버스에 [정방향 | 좌우반전]을 한 번 그려두고, tile()은 그 캔버스를 모듈로로
     이어붙이기만 한다. per-frame translate/scale(-1,1) 제거.
   - 이음새 1px 오버랩 처리는 기존 동작 유지.
3) **시각적 결과는 현재와 동일해야 한다.** MID_SATURATE/MID_BRIGHTEN/MID_CONTRAST/MID_PIVOT/
   MID_BLUR_SCALE 값은 건드리지 말 것(CLAUDE.md: 중경 v2는 필터 보상 선적용 — 필터 변경 금지).
   축소 후 처리라 블러 반경이 소스 비율 기준이면 그대로 유지되지만, 결과가 눈에 띄게 달라지면
   보고만 하고 임의 조정하지 말 것.
4) groundImage getter는 지형 렌더러가 텍스처로 쓰므로, 프리스케일 캔버스를 반환해도
   기존 호출부가 깨지지 않는지 확인(LayerSource 계약 유지).

검증: 인게임에서 rAF FPS 프로브로 최적화 전/후 평균 FPS를 측정해 수치로 보고.
스크린샷으로 4개 라운드 테마 배경이 전과 동일하게 보이는지 대조.
```

```
[클로드코드 프롬프트 — E8-3]
lib/sfx.ts를 HTMLAudioElement에서 Web Audio API로 바꿔라. iOS에서 play() 호출마다 생기는

6) 호출부(GameEngine/player) 시그니처는 바꾸지 말 것.

검증: 모바일에서 코인 연속 획득 구간 FPS 비교, 12종 전부 소리 나는지 확인.
```

## E3.31. 로비 라운드 게이지 늦은 등장 (2026-07-31 실기기)

현상: "퇴근 시작" → 로비 진입 시 상단 라운드 진행바가 없다가 뒤늦게 나타나며 아래 요소가
밀린다(레이아웃 점프).

원인: `Game.tsx` 약 1055행 `{season && <RoundGauge ... />}` — `fetchSeason`이 비동기라
응답 전까지 게이지가 아예 렌더되지 않는다. 응답이 오는 순간 높이가 생기면서 전체가 내려앉는다.

부수 문제: 약 336행 `eng.setEndless("map1", season?.round)`. season 로드 전에 무한 잔업을
시작하면 round가 undefined로 들어가 **1라운드 테마(낮)로 시작**한다. 실제 라운드가 3이면 색이
다르게 나온다.

```
[클로드코드 프롬프트 — E3.31]
로비 라운드 게이지가 늦게 나타나 레이아웃이 점프하는 문제를 고쳐라.

1) **자리 예약(스켈레톤)**: season이 null이어도 RoundGauge와 동일한 높이의 자리를 차지하게 한다.
   조건부 렌더를 없애고, RoundGauge가 season 없이도 렌더되되 내용만 비우는 방식이 깔끔하다.
   - 트랙(gauge_track.webp)과 마커 4개는 그대로 그리고, 마커는 전부 locked 상태로,
     D-day·"n/4 라운드" 텍스트 자리는 빈 문자열 또는 옅은 플레이스홀더로.
   - 로드 완료 시 내용만 채워지고 **높이는 변하지 않아야 한다.**
2) **직전 시즌 값 캐시**: localStorage에 마지막 season 응답의 round/endsAt을 저장해두고
   (키 예: yarikkiri.season.last), 재방문 시 즉시 그 값으로 게이지를 그린 뒤 서버 응답이 오면
   갱신한다. 닉네임이 캐시→서버 갱신하는 기존 패턴과 동일하게.
   첫 방문(캐시 없음)에만 1)의 빈 상태가 보인다.
3) **라운드 테마 누락 방지**: season 로드 전에 무한 잔업을 시작하면 setEndless의 round가
   undefined가 되어 1라운드 테마로 시작한다. 2)의 캐시 값을 폴백으로 넘겨서 이 경우를 막아라.
   캐시도 없으면 현재 동작 유지(기본 테마).
   ⚠️ setEndless 호출부가 season을 deps에 물고 있어 season 도착 시 엔진 재생성이 일어날 수 있다.
   플레이 중 재생성이 발생하지 않는지 확인하고, 발생하면 보고할 것(임의로 구조 바꾸지 말고).
4) LobbyHero의 티어·시즌 성적 표시도 같은 이유로 늦게 나타나는지 확인하고, 그렇다면 같은
   방식으로 자리를 예약할 것.

검증: 네트워크를 느리게(Slow 3G) 설정하고 로비에 진입해 게이지 자리가 처음부터 유지되는지,
값만 채워지는지 스크린샷 2장(로딩 중 / 로드 후)으로 비교. 레이아웃 점프 없어야 함.
```

## E3.32. 로비 우상단 HUD 확대 — 터치 영역·시인성 (2026-07-31 실기기)

현상: 티켓 바·설정·나가기가 화면 대비 너무 작아 모바일에서 터치가 잘 안 먹는다.
쿠키런처럼 버튼이 두드러졌으면 한다는 요청.

원인(코드 실측): 티켓 아이콘 h26 / 캡슐 fontSize 14·padding 4px / + 버튼 h27 /
설정·나가기 h34. **버튼의 터치 영역이 이미지 크기와 동일**해서 모바일 최소 권장치 44px에
못 미친다. + 버튼 27px가 특히 작다.

```
[클로드코드 프롬프트 — E3.32]
로비 우상단 HUD(TicketBar / SettingsButton / ExitButton)를 확대하고 터치 영역을 확보하라.
구조·기능은 그대로 두고 치수만 조정한다.

1) **터치 영역 44px 확보(최우선)**: 각 <button>의 시각 크기와 무관하게 히트 영역이
   최소 44×44가 되게 padding으로 확보하라. 아이콘을 키우는 것과 별개 작업이다.
   레이아웃이 밀리지 않게 padding은 넣되 시각적 배경은 늘리지 말 것
   (투명 패딩 또는 ::before 확장 히트박스).
2) **시각 크기 확대** — 세로 공간이 빠듯한 가로 화면을 고려해 고정값이 아니라 clamp로:
   - SettingsButton / ExitButton: h34 → clamp(38px, 5.4vh, 48px)
   - 티켓 아이콘: h26 → clamp(30px, 4.6vh, 40px)
   - + 버튼: h27 → clamp(32px, 4.8vh, 42px)
   - 캡슐 숫자: fontSize 14 → clamp(16px, 2.4vh, 20px), padding·minWidth(64)도 비례 확대
   - 아이콘이 캡슐에 겹치는 marginRight -14 / marginLeft -13 오프셋은 새 크기에 비례해 재계산
     (겹침 비율 유지 — 지금 룩을 깨지 말 것)
3) 좌상단 "누적 m" pill도 우상단과 균형이 맞게 같은 비율로 키워라. 혼자 작으면 어색하다.
4) 눌림 피드백 추가: 버튼 :active에서 transform scale(0.94) + 그림자 축소.
```

## E3.34. 출석 보상 (2026-07-31)

로비에 일일 출석 체크를 추가한다. **7일 반복 · 누적형 · 보상은 티켓.**

### 확정 사양

- **주기**: 7칸 달력. 7일차를 받으면 다음 바퀴 1일차로 리셋(한 달 이벤트 = 약 4바퀴).
- **누적형**: 하루 빠져도 초기화되지 않는다. "연속 출석"이 아니라 **"방문한 날 수"** 기준으로
  다음 칸을 하나씩 연다. 하루에 한 칸만 받을 수 있다(KST 날짜 기준).
- **보상**: 티켓만. 1~6일차 1장, **7일차 3장**.
- **노출 시점**:
  - 기존 유저: 타이틀에서 "퇴근 시작" → **로비 진입 전에 출석 팝업**
  - 신규 유저: "퇴근 시작" → 닉네임 설정 완료 → 출석 팝업 → 로비

### ⚠️ 앱팀 의존 (선행 필요)

**티켓 지급 권한은 웹에 없다.** 재화 지급·차감은 네이티브/가다 서버 권위이고, 웹은 요청만 한다
(`lib/tickets.ts`는 표시용 로컬 스텁, 광고 티켓도 `requestNativeAction("watchAdForTicket")`).

따라서 `NativeAction`에 **`claimAttendanceReward`** (또는 앱팀이 정한 이름)를 추가하고,
네이티브가 실제 지급을 처리해야 한다. **어뷰징 방지를 위해 "며칠차인지·몇 장인지"를 웹이
정해서 보내면 안 된다** — 웹은 "출석 보상 지급 요청"만 보내고, 몇 장을 줄지는 서버가
출석 기록을 보고 판단하는 구조가 안전하다.

앱팀 회신 전까지는 **스텁으로 먼저 구현**한다(로컬 티켓 +N, 광고 티켓과 동일한 방식).

### 데이터 (Supabase)

E7-0 스키마에 테이블 1개 추가. `users`에 붙이지 말고 별도 테이블로:

```sql
create table if not exists attendance (
  user_id     text not null references users(user_id) on delete cascade,
  claim_date  date not null,            -- KST 기준, 하루 1행
  day_index   int  not null,            -- 이번 바퀴 몇 일차(1~7)
  reward      int  not null,            -- 지급 티켓 수
  created_at  timestamptz not null default now(),
  primary key (user_id, claim_date)
);
alter table attendance enable row level security;
grant all on table attendance to service_role;
```

`day_index`는 서버가 계산한다: 해당 유저의 기존 출석 행 수를 7로 나눈 나머지 + 1.

## E8-5. 조작 대칭화 — 양손 모두 점프·슬라이드 (2026-07-31)

현상: 오른손은 한 손으로 점프·슬라이드 모두 되는데 왼손은 슬라이드만 된다.

원인: `Game.tsx` `onPointerDown`이 `rx < 0.5`(왼쪽 절반)이면 즉시 `eng.slide()` 후

`if (!p || p.slide) return`에서 바로 빠져나가고, 왼쪽에는 점프 경로가 아예 없다.
오른쪽은 `eng.onTap()`(점프) + 스와이프 슬라이드라 둘 다 가능.

결정: **화면 좌우 구역 구분을 없애고 양쪽 동일하게 "탭=점프 / 아래 스와이프=슬라이드"**
(현재 오른쪽 절반 방식을 전체에 적용).

```
[클로드코드 프롬프트 — E8-5]

1) onPointerDown: rx < 0.5 분기를 제거하고, 위치와 무관하게 hud.phase === "playing"일 때
```

## E6-5. 난이도 상향 — 후반 램프 (2026-07-31) — **보류**

> **보류 결정(2026-07-31)**: 내부 테스트 참여자 연령대가 다양하므로, 실제 반응을 본 뒤
> 상향 여부와 폭을 정한다. 아래 설계안은 그대로 두고 테스트 후 재검토.
>
> **테스트 시 확인할 것**: 연령대별 첫 판 생존 시간, 첫 판 이탈 여부, "너무 쉽다/어렵다"
> 주관 평가. 특히 **연령대별로 반응이 갈리는지**가 핵심 — 갈린다면 전체 상향이 아니라
> 아래의 "후반만 가파르게" 방식이 정답이다.

배경: "조금 더 어렵게" 의견. 다만 **E6에서 의도적으로 낮춘 난이도**라는 점을 먼저 짚어야 한다
(40시드 평균 56.2s → 75.7s). 타깃이 40~60대 라이트 유저라 접근성이 설계 전제였다.

**전 구간을 균일하게 어렵게 만들면 안 된다.** 초반이 어려워지면 신규·라이트 유저가 첫 판에서
이탈하고, 이벤트 참여율 자체가 떨어진다. 랭킹 게임에서 필요한 건 "모두에게 어려움"이 아니라
**실력 차이가 점수 차이로 벌어지는 구조**다.

### 방향: 초반 유지 · 후반 가파르게

| 구간 | 처리 | 효과 |
|---|---|---|
| 0~45초 | **현행 유지** | 라이트 유저의 첫 경험·이수율 보호 |
| 45초~ | 램프 가속 | 숙련자 구간. 1초 더 버티는 가치가 커짐 |

이렇게 하면 약한 플레이어의 생존 시간은 거의 그대로고, 잘하는 플레이어만 더 멀리 간다.
점수 분포의 꼬리가 길어져 **랭킹 변별력이 올라간다.**

```
[클로드코드 프롬프트 — E6-5]
엔들리스 난이도를 후반부 중심으로 올려라. **초반 45초는 현재 체감을 유지**하는 것이 조건이다.

1) 시간 기반 램프를 도입해 아래 값들이 45초 이후부터 점진 강화되게 한다
   (config.ts에 RAMP 구간 상수를 두고, 하드코딩 분기 금지):
   - SPEED.MAX 560 → 후반 상한 620 (ACCEL 3은 유지 — 초반 가속감은 그대로)
   - SPAWN.OBSTACLE_MIN/MAX_MS 1400~2400 → 후반 1150~2000 (E6 이전 값 근처까지만)
   - CHASE.RECOVER_PER_SEC 22 → 후반 19 (회복이 느려져 실수 누적이 아프게)
   - SPAWN.FENCE_FROM_S 35는 유지(이미 중반 요소)
   - 투척 램프(PROJECTILE RAMP 90s)는 70s 정도로 당기되 EARLY/LATE 시작값은 유지
2) **OBSTACLE_MIN_INTERVAL_S 0.7과 클리어런스 게이트는 절대 건드리지 말 것.**
   속도가 올라가면 체공 거리 조건이 빡빡해진다. `npm run gate:clearance`가 PASS해야 하고,
   실패하면 속도 상한을 낮춰서 맞춰라(간격을 줄이는 방향 금지).
3) 안전교육(edu) 모드와 route 모드는 **일절 변경하지 말 것.** 이 작업은 엔들리스 전용이다.

검증(필수):
- .simtest 밸런스 sim 40시드 재실행. **다음 3개를 표로 보고**:
  · 평균·중앙값 생존 시간 (변경 전 75.7s / 중앙 70.9s 대비)
  · p25 (약한 플레이 대역) — **여기가 크게 떨어지면 실패**. 58.4s에서 큰 하락이 없어야 한다
  · p75 (숙련 대역) — 93.6s 대비 늘어나야 성공
- 목표: p25는 유지(±5s), p75는 상승, 평균은 65~70s 근처.
- lowbar·fence 피격률이 초반 구간(0~45s)에서 오르지 않았는지 확인.
- 클리어런스 게이트 PASS.
sim 결과가 목표와 다르면 수치를 임의로 더 조이지 말고 **결과를 먼저 보고할 것.**
```

## E8-4-1. 세로 화면 대응 — 회전 잠금 유저 구제 (2026-07-31)

가다가 **순수 웹앱**으로 확인되어 앱 차원의 가로 고정이 불가능하다.

현행은 세로 감지 시 "가로로 돌려주세요" 안내다. 문제는 **화면 회전 잠금을 켜둔 유저는
폰을 돌려도 화면이 안 돌아간다**는 것. 타깃 연령대에서 회전 잠금 사용률은 낮지 않아
그대로 두면 진입 자체가 막힌다.

결정: **세로일 때 게임을 90도 눕혀서 화면을 꽉 채운다.** 안내 문구와 병행한다.

```
[클로드코드 프롬프트 — E8-4-1]
전제: E8-4(세로 감지 수정 — matchMedia 대신 innerHeight > innerWidth 기준)를 먼저 적용할 것.

세로 화면에서 게임을 90도 회전해 표시하는 폴백을 추가하라.

1) 세로로 판정되면 게임 컨테이너에 transform: rotate(90deg)를 적용하고,
   width/height를 서로 바꿔(가로=화면 높이, 세로=화면 폭) 세로 화면을 꽉 채우게 한다.
   transform-origin과 위치 보정을 정확히 잡아 잘리는 부분이 없어야 한다.
2) **입력 좌표계가 함께 회전해야 한다.** 포인터 이벤트의 clientX/clientY를 그대로 쓰면
   탭·스와이프 방향이 어긋난다. E8-5의 "아래로 스와이프 = 슬라이드"가 회전 상태에서도
   맞게 동작하는지 반드시 확인할 것.
3) 안내는 없애지 말고 바꾼다: 회전 표시가 적용된 상태에서 "폰을 돌리면 더 편해요" 수준의
   가벼운 안내를 짧게(3~4초) 띄우고 사라지게. 기존 RotateHint의 전체 차단 방식은 폐기.
4) 가로로 전환되면 즉시 회전을 해제하고 정상 렌더로 복귀. resize/orientationchange 양쪽에서
   재평가.
5) 랭킹 페이지(app/ranking/page.tsx)에도 같은 패턴을 적용할지 판단해 제안할 것
   (랭킹은 정보 화면이라 세로 전용 레이아웃이 나을 수도 있다 — 임의 결정 말고 보고).

검증: puppeteer로 세로 뷰포트(375×812)에서 스크린샷 — 게임이 화면을 꽉 채우는지,
가로 전환 시 정상 복귀하는지. 회전 상태에서 탭 점프·아래 스와이프 슬라이드가
의도대로 먹는지 입력 테스트 결과 포함.
```

## E9. 오픈 전 체크리스트

렉 해소·배포·DB 연동이 끝나면서 남은 항목이 흩어져 있어 한곳에 모은다.
**이 목록은 이벤트 오픈 전에 전부 닫혀야 한다.**

### 반드시 (오픈 차단 요소)

1. **`SEASON.EVENT_START` 교체** — 현재 개발용 `2026-07-13`. 실제 이벤트 시작 월요일로 바꾸지
   않으면 유저가 첫날부터 3~4라운드 화면을 보고, 라운드·D-day·랭킹 집계가 전부 어긋난다.
   `app/game/engine/config.ts`.
2. **Suno 플랜 확인** — BGM "Hard Hat Dash"의 상업적 사용 권리는 유료 플랜 생성분에만 붙는다.
   무료 플랜 생성분이면 사용 불가 → `tools/bgm_gen.py`의 자체 칩튠으로 교체(라이선스 자유).
3. **가다 앱 웹뷰 브리지 E2E** — `/game?token=...&debug=1`로 열어 BridgeDebug 패널의 채널 감지가
   `ReactNativeWebView` 또는 `webkit`으로 잡히는지 확인. 티켓 차감·광고·결과 전달이 실제로
   네이티브에 도달하는지까지 봐야 한다(브라우저 단독으로는 검증 불가).
4. **디버그 패널 프로덕션 비활성화** — `?debug=1` 게이트가 있어 일반 유저에겐 안 보이지만,
   패널에 네이티브 액션 테스트 발사 버튼(광고 티켓 등)이 있다. 재화 권위는 네이티브/서버에
   있어 실제 지급까지 가진 않더라도, 오픈 시엔 프로덕션 빌드에서 꺼두는 편이 안전하다.

### 웹앱 확정에 따른 재검토 (2026-07-31)

가다가 순수 웹앱으로 확인되어 아래 전제가 깨졌다. **오픈 전 방향 확정 필요.**

- **광고 티켓 충전(`watchAdForTicket`)**: **목적은 수익**(마찰 장치가 아님 — 2026-07-31 확인).
  네이티브 광고 SDK를 쓸 수 없으므로 웹 리워드 광고 네트워크(H5 게임용) 도입 검토가 필요하다.
  판단에 필요한 것: ① 예상 DAU와 그에 따른 예상 수익 규모 ② 광고 네트워크 승인·정산 준비 기간
  ③ **광고 수익이 붙을 때 게임물 등급분류·게임제작업 등록 의무가 강화되는지 법무 확인**
  (이미 진행 중인 경품 관련 법적 검토에 함께 올릴 것). 결론 전까지 "광고 +1" 버튼 노출 여부 보류.
- **푸시**: 웹 푸시는 iOS에서 홈 화면 설치 유저만 도달. 리텐션 축에서 제외하고
  알림톡·문자 등 대체 수단을 검토 중.
- **가로 고정**: 앱 차원 강제 불가 → E8-4-1로 웹에서 해결.
- **재화 권위**: 네이티브가 아니라 **가다 웹 서버**가 권위를 갖는다. 브리지는
  `window.parent.postMessage`(iframe) 채널을 쓰거나, 서버 간 연동으로 갈지 앱팀과 확정 필요.

### 앱팀 요청 사항 (웹에서 제어 불가)

5. 웹뷰를 **주소창 없는 전체화면**으로 띄울 것. 현재 인앱 브라우저로 열면 상단 주소창이
   화면을 잡아먹는다.
6. **가로 모드 고정.** 세로로 열리면 게임이 화면의 1/5만 차지한다.
7. 당겨서 새로고침(pull-to-refresh) 비활성화 — 플레이 중 오작동 방지.

### 남은 개선 (오픈 후로 미뤄도 되는 것)

8. **라운드 이름 붙이기(E5-2 예정)** — 라운드마다 배경색이 바뀌는데 이유가 안 드러나 유저가
   "화면이 왜 이래?"로 읽는다. 낮→석양→황혼→야간을 "오전 작업 / 해질녘 / 야근 돌입 /
   철야 현장" 식으로 명명해 로비 게이지·랭킹 헤더·시작 배너에 표기.
   **3라운드 색이 모바일에서 형광 분홍으로 읽히는 문제도 같이** — `ROUND_THEMES` dusk의
   hue -48 완화 검토. 카드/배경 아트도 라운드별 변형이 필요하면 이때 같이 뽑는다.
9. **결과 화면에 대사 잔류** — 게임오버 오버레이가 뜬 뒤에도 직전 대사("내일 아침 일찍 나와" /
   "김반장: ...네, 소장님")가 점수 카드 뒤에 깔려 잘린 채 보인다. 오버레이 진입 시 대사를
   정리할 것.
10. **세로 모드 안내 미작동(E8-4)** — `matchMedia("(orientation: portrait)")`가 실기기에서
    false로 나와 RotateHint가 안 뜬다. `innerHeight > innerWidth` 기준으로 교체.
11. **userId 위조 방어** — 가다 서버의 서명 토큰 검증(아래 "서버·앱 팀 의존" 참고).
