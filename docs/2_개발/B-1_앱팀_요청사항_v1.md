# B-1. 가다 앱팀 요청사항 정리 v1 (2026-08-03)

> 대상: 가다 앱 개발팀 리드. **모든 항목에 "왜 필요한지(당위성)"와 "미이행 시 영향"을 명시**했습니다.
> 기술 상세(페이로드·채널·코드 위치)는 `B_네이티브_연동명세서_v1`을 참조하세요. 이 문서는 의사결정·일정 협의용입니다.
> 우선순위: 🔴 이것 없이는 정식 오픈 불가 / 🟡 오픈 주까지 / 🟢 오픈 후 개선 가능

---

## 요청 1. 🔴 딥링크 진입 + 유저 토큰(uid) 발급

**요청**: 앱 배너 → `https://gada-minigame1.vercel.app/game?token=<base64url({uid, exp})>` 로 웹뷰를 열어주세요.

**당위성**: 게임의 모든 서버 데이터(랭킹 점수·닉네임·안전교육 이수·출석)가 이 uid를 키로 저장됩니다.
토큰이 없으면 웹은 기기별 게스트 계정으로 동작하는데, 이는 내부 테스트용 임시 장치입니다.

**미이행 시 영향**:
- 유저가 기기를 바꾸거나 앱 데이터를 지우면 **기록·이수·출석이 전부 소실** → CS 문의 폭주 예상
- 게스트 계정은 초기화가 자유로워 **랭킹 어뷰징(계정 리셋 반복)이 가능** — 보상 이벤트에서 치명적
- 명예의 전당·보상 지급 시 "누구인지" 특정 불가

---

## 요청 2. 🔴 브리지 수신 채널 1종 구현

**요청**: RN이면 `ReactNativeWebView.postMessage` 수신, iOS 네이티브면 `webkit.messageHandlers`
(`gameResult`, `nativeAction`) 핸들러 주입 — **둘 중 하나만** 구현하면 됩니다.

**당위성**: 게임 결과 전달, 광고 요청, 보상 지급, 웹뷰 닫기 — 앱↔게임의 모든 상호작용이 이 통로
하나로 갑니다. 웹 쪽은 3채널 모두 이미 구현·배포되어 있어 앱이 핸들러만 꽂으면 즉시 연결됩니다.

**미이행 시 영향**: 아래 요청 3~5가 전부 동작 불가(요청은 허공으로 감). 게임은 돌아가지만
"앱 속 이벤트"가 아니라 "고립된 웹페이지"가 됩니다.

## 요청 3. 🔴 NATIVE_ACTION 처리 — 최소 3종

| action | 앱이 할 일 | 당위성 | 미이행 시 |
|---|---|---|---|
| `exitGame` | 웹뷰 닫기 | 웹은 스스로 창을 닫을 수 없음(브라우저 보안 제약). 로비의 나가기 버튼이 이 요청을 보냄 | **유저가 게임에 갇힘** — 뒤로가기 없는 웹뷰면 앱 강제 종료밖에 없음. UX 치명 |
| `watchAdForTicket` | 리워드 광고 노출 → 완료 시 티켓 +1 | 티켓 소진 후 재도전 수단 = 플레이 루프의 연료이자 광고 수익 지점. 웹은 광고 SDK를 실을 수 없음 | 티켓 소진 = 플레이 종료 → 일평균 플레이 횟수(KPI) 급감 |
| `claimAttendanceReward` | 출석 티켓 지급(1~3장) | 출석 보상은 기획의 1순위 리텐션 장치(매일 접속 이유). 지급 권위는 앱/서버 원칙 | 출석 UI는 있는데 실제 지급이 없으면 **약속 위반** — 신뢰 문제로 이탈 가속 |

나머지 3종(`inviteFriend`, `shareResult`, `exchangePointsForTicket`)은 🟡 — 초대는 K-factor 확보용,
공유는 Web Share 폴백이 있어 후순위, 포인트 교환은 법적 검토 결론까지 숨김 상태입니다.

> ⚠️ 지급 연동이 켜지는 시점에 웹의 개발용 로컬 스텁(+1)을 제거해야 **이중 지급**이 없습니다.
> 연동 일정이 잡히면 웹팀(마케터)에 알려주세요 — 제거는 웹 쪽 1줄 작업입니다.

## 요청 4. 🔴 웹뷰 설정 2가지

**요청**: ① 게임 웹뷰 **가로 고정** ② 스크롤 바운스(오버스크롤) 비활성.

**당위성**:
- 게임이 가로 800×450 고정 설계입니다. 웹에 세로 감지·회전 안내가 있지만, 안내를 보는 것
  자체가 이탈 포인트 — 앱이 가로로 열어주면 첫 화면부터 게임이 보입니다.
- 조작이 "아래로 스와이프 = 슬라이드"인데, 웹뷰 기본 바운스가 켜져 있으면 스와이프가
  화면 스크롤로 새서 **슬라이드가 씹힙니다**. 웹에서도 3중으로 방어하고 있지만 웹뷰 설정이 근본 해결입니다.

**미이행 시 영향**: 첫인상 저하(세로 진입), 핵심 조작 불량 → "조작감 나쁨" 리뷰의 주범.

---

## 요청 5. 🟡 티켓 정책 구현 + 잔량 동기화 (협의 필요)

**요청**: ① 기획의 티켓 정책(일일 2장 자동 지급, 자정 리셋, 미사용 소멸) 구현 주체·일정 확정
② 앱이 지급 권위를 가질 경우, 웹에 잔량을 알려줄 방법 협의(토큰에 포함 or JS 주입 — 명세서 B 2-3절).

**당위성**: "오늘의 티켓이 곧 사라진다"는 기획의 핵심 리텐션 훅(푸시와 연동)입니다. 현재 웹 로컬
카운트는 기기별이라 멀티 디바이스에서 어긋나고, 소멸·리셋을 구현할 수 없습니다. **재화는
클라이언트에 권위를 둘 수 없다**는 원칙(어뷰징)도 이유입니다.

**미이행 시 영향**: 티켓이 사실상 무한(광고 스텁 +1 반복) → 희소성 붕괴, 리텐션 장치 상실,
광고 시청 동기 소멸.

---

## 요청 6. 🟡 푸시 발송 3종

**요청**: ① 티켓 소멸 임박("오늘의 퇴근 티켓 2장이 곧 사라집니다") ② **추월 알림**("김OO님이
방금 당신을 제쳤습니다") ③ 라운드 D-day. 발송 빈도 정책은 마케팅과 협의.

**당위성**: 웹 게임은 스스로 유저를 다시 부를 수단이 없습니다 — 재방문 트리거는 100% 앱 푸시.
특히 추월 알림은 경쟁 심리를 직격하는 기획 1순위 장치입니다(피벗 기획 4장).

**미이행 시 영향**: D1 이후 리텐션이 유저 기억력에만 의존 → 주간 재참여율(핵심 KPI) 목표 달성 난망.

---

## 요청 7. 🟢 GAME_RESULT 수신·보관 (선택)

**요청**: 판 종료마다 오는 결과 JSON을 자체 서버에 적재(선택 사항).

**당위성**: 랭킹 반영은 웹이 자체 처리하므로 게임 동작에는 불필요하지만, 앱 쪽에 기록이 있으면
① 보상 지급 시 교차 검증(어뷰징 수동 검수) ② CS 대응("내 점수가 사라졌어요") ③ 자체 분석이
가능해집니다. `sessionId`로 중복 제거 가능.

**미이행 시 영향**: 없음(게임 정상 동작). 다만 분쟁 시 근거 데이터가 웹 DB 하나뿐.

---

## 요청 8. 🔴 연동 E2E 검증 협조 (반나절)

**요청**: 개발 빌드 웹뷰에서 `...&debug=1`로 접속해 좌하단 🐞 패널과 함께 확인:
① 패널 첫 줄 "감지"에 채널명이 뜨는지(없음=주입 실패) ② 테스트 발사 버튼 4종에 앱이 반응하는지
③ 한 판 플레이 후 GAME_RESULT 수신 확인.

**당위성**: 웹뷰 안에서는 개발자 도구를 못 씁니다. 이 때문에 **화면 위 디버그 패널을 미리 만들어
뒀고**, 앱 개발자가 로그 환경 없이도 즉석에서 연동 상태를 눈으로 확인할 수 있습니다. 스크린샷
한 장이 곧 검증 리포트가 됩니다.

**미이행 시 영향**: 연동 문제를 정식 오픈 후 유저 CS로 발견하게 됩니다.
