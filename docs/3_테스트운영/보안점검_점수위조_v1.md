# 보안 점검 — 점수 위조 방어 v1 (2026-08-06)

> 계기: 내부 프론트엔드 엔지니어가 플레이 없이 `/api/season`에 POST 한 번으로 **90만점** 등록.
> 대상: 개발·운영. 조치 내용과 남은 리스크, 운영 보완책을 정리합니다.

## 1. 취약점 (수정 전)

- `/api/season` POST가 클라이언트가 보낸 `score`·`playDuration`을 그대로 신뢰
- 점수 상한이 `score ≤ playDuration × 130`인데 **playDuration을 클라이언트가 지정** →
  `playDuration: 7000, score: 900000`이면 통과
- **인증·세션 검증 없음** → 아무나 아무 userId로, 플레이 없이 제출 가능

## 2. 조치 (수정 후) — 다층 방어

| 계층 | 내용 | 막는 것 |
|---|---|---|
| ① 서버 발급 세션 | 무한 잔업 시작 시 `/api/session`이 시작 시각 기록 + 1회용 세션 발급 | 세션 없는 "한 방 POST" |
| ② 서버 측정 시간 | 점수 제출 시 서버가 (제출 시각 − 시작 시각) 직접 계산. **클라 playDuration 폐기** | 시간 위조 |
| ③ 최소 시간 | 발급 후 `MIN_PLAY_SEC`(3초) 미만 제출 거부 | 발급 즉시 제출(봇) |
| ④ 경과시간 상한 | `MAX_PLAY_SEC`(900초)로 클램프 → 절대 상한 ≈ 117,200점 | 세션 오래 열어두고 뻥튀기 |
| ⑤ 1회용 소비 | 소비된 세션 재사용 거부(DB `consumed_at` 조건부 update) | 세션 재사용 |
| ⑥ userId 일치 | 세션 발급자와 제출자 불일치 거부 | 남의 세션 위장 |

**검증(스텁 서버 8종 통과)**: 세션 없이 90만=거부 / 즉시 90만=거부 / 4초 후 90만=score_cap /
재사용=거부 / userId 위장=거부 / 정상 4초 500점=통과·랭킹 반영.
프로덕션의 90만점 데이터는 삭제 완료(현 1위 18,196).

## 3. 남은 리스크 (정직한 한계)

- **클라이언트 게임의 본질적 한계**: 점수 계산이 브라우저에서 일어나므로, 공격자가
  "세션 발급 → 스크립트로 N초 대기 → 상한 이내 점수 제출"을 반복하면 **상한 이내의 가짜 점수**는
  여전히 만들 수 있음. 완전 차단은 서버 사이드 게임 시뮬레이션(오버킬)이 아니면 불가.
- 다만 이제 **한 방에 90만 같은 값은 불가능**하고, 부정 점수도 실제 플레이 시간에 비례하는
  대기를 강제받음(효율 급감).
- **인증 부재**: 현재 게스트는 userId만으로 식별 → 타인 userId 사칭 가능성 잔존.
  → **앱 연동 시 서명된 토큰(HMAC)으로 해소**(앱팀 요청서 B-1 요청1). 그전까진 내부 테스트 한정.

## 4. 운영 보완책 (기획 3.3 이행)

- **상위권 수동 검수**: 보상 지급 전 상위권 `game_sessions`·`daily_scores` 로그 대조
  (비정상: 세션 경과시간이 일괄 상한 근처, 동일 간격 반복 등)
- 이상치 모니터링: 특정 userId가 매일 상한 근처 점수를 찍으면 플래그
- 게스트 계정 리셋 어뷰징은 앱 토큰 연동으로 자연 해소(uid 고정)

## 5. 배포 전 필수 (사용자 액션)

1. **README의 `game_sessions` 테이블 SQL을 Supabase에서 먼저 실행** — 실행 전 배포 시
   세션 발급이 실패해 **모든 점수 제출이 막힘**(랭킹 정지). 반드시 SQL → 배포 순서.
2. 배포 후 정상 플레이 1판으로 점수 반영 확인.

## 6. 앱 연동 시 추가 권장 (오픈 전)

- 딥링크 토큰을 HMAC 서명 + 짧은 만료로 발급 → userId 사칭 차단
- `/api/season`·`/api/session`이 토큰 서명을 검증하도록 확장(현 구조에 미들웨어 1개 추가 수준)

# 부록 — 공격 표면 전수 감사 (2026-08-06)

점수 방어 후 전 API 라우트(6개)를 공격자 관점으로 재점검한 결과.

## 이번에 추가 조치한 것

| # | 취약점 | 조치 |
|---|---|---|
| 1 | `/api/session` 무한 발급 → game_sessions 테이블 증식(스토리지·비용 DoS) | 발급 시 해당 userId의 소비완료·TTL(30분) 초과 세션 삭제 + 제출 시 만료 세션 거부 |
| 2 | userId 길이·형식 무검증(과길이·제어문자로 DB/메모리 남용) | `lib/validate.sanitizeUserId`(1~64자·안전문자) 전 라우트 적용 |

## 안전 확인된 것 (조치 불요)

- **XSS**: 닉네임은 React가 자동 이스케이프, 캔버스는 문자열 렌더, innerHTML 미사용
- **score 입력**: `Number.isFinite`+음수 차단+`Math.floor`
- **날짜 위조**: season·attendance 모두 서버 KST 계산(클라 date 폐기)
- **출석 파밍**: 하루 1회 PK 차단, 티켓은 네이티브 권위(웹 API로 미증가)
- **닉네임**: 서버 `validateNickname`(길이·금칙어·문자셋)

## 잔여 리스크 → 앱 연동/인프라에서 해소

| 리스크 | 해소 시점 |
|---|---|
| **인증 부재(userId 사칭)** — 모든 API 공통 근본 | 앱 토큰(HMAC 서명+만료) 연동 시. 라우트에 서명 검증 미들웨어 1개 추가 수준(B-1 요청1) |
| **rate limiting 전무** — log 폭탄 등 | Vercel WAF/rate limit 또는 토큰 기반 쿼터. 오픈 전 인프라 설정 |
| **progress 우회**(교육 스킵) | 게임성 문제·보상 무관. 낮음. 필요 시 세션처럼 이수 검증 |
| **클라 점수 계산 신뢰**(상한 이내 부정 점수) | 완전 차단 불가 — 상위권 수동 검수로 보완(운영) |

**결론**: 오픈 전 반드시 필요한 근본 보완은 **앱 토큰 인증** 하나로 수렴. 나머지 명백한 남용은
이번 조치로 차단됨.
